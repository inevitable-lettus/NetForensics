## Bug
`parse_dns_flows` (`backend/parse/dns_parser.py`) raises `UnicodeDecodeError` on a DNS query whose label is not valid UTF-8. One bad packet aborts the whole analysis, so the case produces no findings at all. Found by Dwight while curating sample pcaps (PR #15).

## Repro
1. Run `scripts/fetch_sample_pcaps.py` from PR #15 to get `dns-iodine.pcap` (iodine DNS tunnel; encodes data in non-text labels).
2. `python -c "from backend.pipeline import analyze_pcap; analyze_pcap('x'*32, 'sample-pcaps/dns-iodine.pcap')"` (or upload it through the API).
3. Observe `UnicodeDecodeError` from the DNS parse. Dwight to attach the exact traceback and the offending packet number.

## Where to look (unverified)
`_iter_dns_queries` only catches `dpkt.dpkt.UnpackError` around `dpkt.dns.DNS(udp.data)`. The decode error most likely escapes from dpkt's name decoding or from the later use of `question.name`; confirm with the traceback before choosing the fix.

## Expected behaviour
A non-UTF-8 label is decoded safely and analysis continues. The decision on *how* to represent such a name belongs in the PR description (for example decode with a replacement/escape policy that is deterministic and keeps the raw bytes recoverable), because it affects the entropy and length features the DNS-exfil detector reads. Non-UTF-8 labels are themselves a tunnelling signal; do not silently drop them.

## Acceptance criteria
- [ ] `analyze_pcap` on `dns-iodine.pcap` completes without exception.
- [ ] A packet with a non-UTF-8 label no longer aborts parsing; remaining packets in the capture are still parsed (test proves queries after the bad packet are present).
- [ ] The chosen decoding is deterministic (same bytes -> same string) and documented in the function docstring.
- [ ] Entropy and length for such labels are computed on the decoded string, with no crash in `shannon_entropy`.
- [ ] Note in the PR what `dns-iodine.pcap` now reports (finding or none); do not tune thresholds here.
- [ ] Function size/nesting limits from CLAUDE.md respected.
